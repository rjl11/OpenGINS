# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

GNSS + IMU fusion firmware for a navigation unit meant to be universal: agricultural (AgOpenGPS / AgOpenWeb) on a tractor, a GNSS survey pole, and a UAV. Don't design for the tractor only. `plans/` holds the design. `firmware/` holds a first demo (sensor bring-up and INSLIB fused output, status on USB, no Bluetooth yet). It builds and its parts have been tested on the bench, but not yet end to end in a vehicle. Host tests for the calibration, pole, speed, ground-point, geoid and flow-link code are in `firmware/tools/test_*.c`; `BUILDING.md` lists the commands.

The target system (see `plans/README.md` for the index):
- **MCU:** Raspberry Pi Pico 2 W (RP2350 + CYW43439), Pico SDK, bare metal. FreeRTOS may come later on core 0 only (`plans/rtos-decision.md`).
- **Sensors:** Unicore UM980 or UM982 GNSS on a ready-made module (USB-C = COM3 for a PC, COM1/COM2 UART pins, PPS, 5 V; 20 Hz binary logs on UART1 → COM1, PPS on a GPIO). The model is detected at boot; the antenna mode (single, or dual with GNSS heading on a UM982) is a compile-time default the web page can override, applied after a reboot (`plans/gnss-um98x-config.md`). Also a TM210 IMU (800 Hz raw data only on UART0 at 921600; the MCU configures it at boot, `plans/imu-tm210-config.md`, and never sends TM210 calibration commands), BMP581 barometer (100 Hz on I2C1).
- **Filter:** INSLIB `nav_suite` (`external/INSLIB`). It needs no heap, all its state sits in `nav_suite_t`, and its worst-case stack is about 13 KB (`plans/inslib-nav-suite.md`).
- **Links:** BLE NUS (Classic SPP as fallback) to SW Maps on Android carries NMEA out at 10 Hz and RTCM in. Each CRC-checked RTCM frame goes to the receiver's COM1 on UART1, the same port that carries commands and logs (`plans/rtcm-over-bluetooth.md`). The Pico uses only COM1 (COM3 is the module's USB-C, left for a PC; COM2 goes to the Zero 2 W companion if fitted), and no receiver port is ever locked (`CONFIG RXTYPE` risks bricking it). The MCU configures the receiver itself at boot (`plans/gnss-um98x-config.md`).
- **Wi-Fi web server** for diagnostics and configuration (`plans/web-config-server.md`). During development it is always on and joins the network set by `-DWIFI_STA_SSID` as a station, falling back to the open access point `OpenGINS`; a production build (`-DWEB_MODE=switch`) starts Wi-Fi only when GPIO22 is pulled to GND at boot.
- **On hold:** W5500 Ethernet / `$PAOGI` output. Its pins (SPI0, GP16–21) stay reserved, so don't assign them to anything else.

## Core split (applies to all firmware code)

- **Core 1:** only the INSLIB filter, in a plain loop with nothing that preempts it. It pops samples from a core 0 queue and makes one `nav_suite_update()` call per IMU sample (800/s); when no IMU sample has come for 50 ms it also runs an epoch without IMU every 50 ms, so INSLIB sees an IMU loss and stops (mode NONE) instead of its last solution staying published. While the filter is down the outputs take the receiver's position (`best_position()` in `main.c`). Every 100 ms it publishes its outputs for core 0 to read.
- **Core 0:** UART DMA, the sensor parsers, the BMP581 driver, Bluetooth (BTstack via `pico_cyw43_arch_threadsafe_background`) and the RTCM forwarder. Write this code as separate modules with queues between them, so a later move to FreeRTOS stays small.
- Take sample timestamps (`time_us_64()`) in the ISR or DMA-complete handler, not when the sample is processed. INSLIB handles measurement delay but needs accurate capture times.
- Put the filter's hot path and the timestamping ISRs in SRAM (`__not_in_flash_func` or RAM section placement) for deterministic timing. A whole-image `copy_to_ram` build won't fit once Wi-Fi is linked in (`plans/web-config-server.md`, "Memory layout").

## Firmware layout and build

- `firmware/CMakeLists.txt` is the project (board `pico2_w`, flash binary with the core 1 path in SRAM through the linker override in `firmware/link/`; stdio on USB only, because UART0 is the TM210). After a build, `python firmware/tools/check_ram_path.py firmware/build/app.dis` (run from the repo root; it defaults to `build/app.dis`, relative to `firmware/`) must report nothing reachable from core 1 or the ISRs in flash; when core 1 starts calling a new SDK or libc function, add its file to `firmware/link/default_text_excludes.incl`.
- `firmware/app/`: `main.c` (core 0 loop and the 1 Hz status report), `nav_core1.c` (the filter on core 1 and its queues), `cpu_load.h` (header-only load meter for both cores' polling loops, timed with each core's SysTick because the M33 has no DWT cycle counter; each loop flags its work passes, and idle passes are charged the mean of the typical idle pass; shown as the `CPU` lines and `cpu` in `/status.json`; a FreeRTOS move would take the SysTick, so switch to its idle hook then), `die_temp.c` (the RP2350's on-chip temperature sensor on the internal ADC input, read with the status report; uncalibrated, so a few degrees off; nothing else uses the ADC, and ADC input 3 / GP29 must never be read because the CYW43439 shares it), `app_config.h` (mounting, noise figures, options), `settings.c` (web-page settings in flash, including the sensors fitted: barometer, magnetometer, optical flow, wheel pulses, each on/off and applied live; new fields are appended and `settings_load()` migrates older records by size), `flash_rec.c` (the two-sector flash record both use), `imu_calib.c` with `imu_calib_fit.c`, `imu_calib_acc.c`, `imu_calib_mag.c`, `imu_calib_rot.c` and the shared solver `imu_calib_lsq.c` (gyro bias vs temperature and scale / misalignment, the accelerometer from static poses and the magnetometer, learned in the background, applied at boot, managed on the web page `calib.html`; host tests `firmware/tools/test_imu_calib_*.c`), `field_io.c` (the wheel / ground-speed inputs and the optical-flow link on core 0: status figures and the raw pulses per metre; wheel speed not fused yet), `flow_nav.c` (the Pi's flow to a ground speed: frame matching by the left-out trigger pulse, strobe timing, gyro de-rotation, tilt-corrected height, lever arm, 10 Hz averaging; pushed with `nav_push_speed()` into INSLIB's speed input on core 1, a queue shared with wheel speed later; camera height, image direction and lever arm on the web config page, defaults in `APP_FLOW_*`; host test `firmware/tools/test_flow_nav.c`), `geoid.c` with the generated `geoid_grid.c` (geoid height for `h_geoid_m` in `/status.json` and the USB status: Lantmäteriet's SWEN17_RH2000 cut to 100 km around the RTK base by `firmware/tools/geoid_cut.py` from `geoid/SWEN17_RH2000.txt` (source and format in `geoid/README.md`); an RH 2000 height only with RTK from the SWEREF 99 base; outside the grid the receiver's undulation; host test `firmware/tools/test_geoid.c`), `ground_point.c` (tractor / survey pole: with the web setting `ant_height_m` above 0, `best_position()` outputs the ground point below the antenna, the IMU point moved by the lever arm plus the height along the body down axis, tilted only while the INS attitude passes `APP_GROUND_TILT_MAX_SD_DEG`, else straight down; host test `firmware/tools/test_ground_point.c`), `pole_aid.c` (survey pole on core 1, in SRAM: planted-tip detector, the tip held through INSLIB's lever-armed local-position input, a linear yaw fix per planted sway, and a magnetometer trust gate; `plans/pole-tilt-aiding.md`, thresholds `APP_POLE_*`; host test `firmware/tools/test_pole_aid.c`), `pole_mount.c` with `pole_mount_fit.c` (survey pole on core 0: the IMU's tilt against the pole axis, learned from the twist of planted episodes that `pole_aid` sends through a queue, kept in its own flash record, applied at boot to the tip lever arm and the ground point, managed on `calib.html`; the pole length only checked against `ant_height_m`; `plans/pole-tilt-aiding.md` item 5, thresholds `APP_POLE_MOUNT_*`; host test `firmware/tools/test_pole_mount.c`), `usb_log.c` (the field-test log mode: `log on` on the USB port streams every sensor, the INSLIB output, the speed edges and the flow link as framed binary records, with printf going into TEXT records; recorded and decoded with `firmware/tools/field_log.py`, which reconnects after a Pico reboot and gives every row a GPS time from the GNSS / TIME records, `plans/wheel-odometry-aiding.md`, "Field testing").
- **Every pin, bus instance and baud rate is in `firmware/app/board_pins.h`.** No other file names a GPIO number; drivers get their pins through their config structs.
- `firmware/drivers/`: `uart_dma` (DMA ring receive, polled transmit), `tm210` and `um980` (parser plus boot check/provision state machine each; `um980` drives both the UM980 and the UM982), `bmp581`, `inslib` (CMake wrapper around `external/INSLIB`), `pulse_in` (edge timestamps from the two speed inputs), `flow_io` (camera trigger PWM, strobe timestamps, receive-only PIO UART for the flow link). The GPIO raw handlers each take an SDK shared-IRQ slot, so the app raises `PICO_MAX_SHARED_IRQ_HANDLERS` (a hard assert at boot otherwise); the PWM interrupt is exclusive to `flow_io`.

Build on the Windows PC (reload `Path`, `PICO_SDK_PATH`, `picotool_DIR` and `pioasm_DIR` from the User environment first if the shell is stale):

```bash
cmake -S firmware -B firmware/build -G Ninja
ninja -C firmware/build
```

The output is `firmware/build/app.uf2` (and `app.elf` for SWD). The GNSS antenna mode defaults to single; add `-DGNSS_ANTENNA_MODE=dual` to the cmake line for a UM982 with two antennas. `-DPLATFORM=pole` (default, with an antenna height of 2 m, `APP_ANT_HEIGHT_M`), `tractor`, `multirotor` or `fixed_wing` sets when the GNSS course counts as a heading for the magnetometer calibration; the web page can override it (at reboot). The web server is on by default (`-DWEB_MODE=always`, joins the network named by `-DWIFI_STA_SSID`, open unless `-DWIFI_STA_PASSWORD` is set); `-DWEB_MODE=switch` starts it only when GPIO22 is pulled to GND at boot; `-DWEB_MODE=off` builds without Wi-Fi. `-DWIFI_MODE=auto` (default) falls back to the open AP `OpenGINS` (192.168.4.1) when the station hasn't joined within 30 s of boot and stays there until reboot; `sta` never starts the AP, `ap` runs it from boot. Its code is in `firmware/app/web/` with `firmware/app/lwipopts.h`; the AP's DHCP/DNS servers are vendored in `firmware/drivers/ap_servers/`. Flashing, debugging, the host tests and builds on small hosts are in `BUILDING.md`.

## Pi-side code and shared headers

- `pi/flow/`: optical flow on a Raspberry Pi with the OV9281 camera, sent to the Pico (`pi/flow/README.md`, `plans/optical-flow-aiding.md`). C++17 with CMake; OpenCV and libcamera come from the OS packages (`libopencv-dev`, `libcamera-dev`), never as submodules. Build with `cmake -S pi/flow -B pi/flow/build -G Ninja` and `ninja -C pi/flow/build`, test with `pi/flow/build/test_flow`. `pi/flow/python/` is the first Python version, kept as the reference. Linux code for the Pi goes under `pi/`, one folder per program. Clone on the Pi without `--recursive`; it needs no submodule.
- `common/`: headers shared by the Pico firmware and the Pi code. `common/flow_link.h` is the flow link format, used by the C++ program directly; `pi/flow/python/flow_link.py` mirrors it, and `firmware/tools/test_flow_link.c`, `pi/flow/tests/test_flow.cpp` and `pi/flow/python/test_flow_link.py` all check the same example frame, so change both sides in one commit.

## Drivers

Each driver in `firmware/drivers/<name>/` is a Pico SDK static library with its own `CMakeLists.txt`. The firmware project pulls it in after `pico_sdk_init()` with `add_subdirectory(drivers/<name>)` and `target_link_libraries(app PRIVATE <name>)`. Vendor code is a git submodule in `external/`, compiled into the driver library from its path relative to the driver.

`firmware/drivers/bmp581` is the pattern to follow. It is thin glue around Bosch's API, with I2C timeouts so a stuck bus can't hang core 0, and an INT-pin edge timestamp that is read later by `bmp581_poll()` from the main loop. It is not thread safe and runs on core 0. Driver error codes are below -100, so they don't collide with the vendor's negative codes. It defines `BMP5_USE_FLOATING_POINT` because the RP2350 has an FPU.

## Submodules

```bash
git submodule update --init --recursive
```

- `external/INSLIB`: the navigation filter. It has its own `Makefile`, tests, `coding_style.md` and requirement docs (`requirements/`). Plans cite its headers (`src/nav_suite.h`, `src/ins.h`) as the source of truth.
- `external/BMP5_SensorAPI`: Bosch BMP5 driver.
- `external/Adafruit_BMP5xx`: Adafruit's Arduino library for the BMP580/581/585, kept only as a usage reference for `firmware/drivers/bmp581` (setup order, oversampling/ODR/IIR settings, interrupt config in `src/Adafruit_BMP5xx.cpp` and `examples/`). It is not compiled: its `src/` carries its own copy of Bosch's `bmp5.c`, which would clash with `external/BMP5_SensorAPI`.

- `external/CAM-OV9281RAW-V2`: INNO-MAKER's repo for the CAM-MIPI9281RAW-V2 (OV9281 global-shutter camera for the Raspberry Pi, bought for optical flow, `plans/optical-flow-aiding.md`): user manual PDF, trigger tools in `ov9281_libcamera/`, old drivers in `Legacy/`. Reference only, nothing here builds it.

Not a submodule: `external/syd_dynamics` is a plain vendored copy of SYD Dynamics' TransducerM examples and the TM210 3D model. It is the EasyProfile protocol reference for the TM210 (see its `README.md`), and it is not compiled. `temp/` is git-ignored scratch space.

## Plans and docs

- Each plan in `plans/` starts with a **Context** section, cites datasheets by their path in `docs/`, and links related plans by relative link. When adding, renaming or shelving a plan, update the table in `plans/README.md` (shelved plans go under "On hold").
- A hardware or architecture decision usually touches several plans (for example, the pin/UART table in `rp2350-feasibility.md`, the core split in `rtos-decision.md` and the companion plans). Keep them consistent.
- PDFs live in `docs/datasheets/` (component datasheets) and `docs/` (manuals and guides, e.g. the Unicore N4 commands manual). Grep `plans/` for a PDF's path when moving it.
- `docs/firmware/unicore/` holds UM980 / UM982 receiver firmware (`.pkg`, latest build per model) with release notes and English translations in its `README.md`. It is flashed with UPrecise over the module's USB-C (COM3), never from the Pico.
- Open work items are kept in `TODO.md` at the repo root, each linking to the plan that holds the details.
- Figures marked "estimate, not yet measured" in the plans are unverified. Don't present them as measured.
- The public repo (OpenGINS) does not carry the vendor PDFs, the receiver firmware images, the bench records in `docs/` or `external/syd_dynamics`; `docs/NOT_INCLUDED.md` lists what the plans cite. Don't assume those paths exist there.
